# Notepad++ on macOS

A native macOS build of Notepad++ made from upstream's own source. **Nothing under `PowerEditor/`,
`scintilla/`, `lexilla/` or `boostregex/` is edited for macOS**, so fixes and features from
[notepad-plus-plus/notepad-plus-plus](https://github.com/notepad-plus-plus/notepad-plus-plus) merge
without conflicts. Everything macOS-specific lives in this directory.

This is an unofficial port; it is not made, endorsed or supported by the Notepad++ project.

## How it works

```
upstream PowerEditor/src ──► engine/ (npp-migrate) ──► <build>/generated/PowerEditor/src ──► clang ──► app
                                                                          ▲
                                       runtime/ (Win32 API on macOS) ─────┘
```

Two differences between Windows and macOS cannot be hidden by a library, and two can:

| Difference | Handled by |
|---|---|
| `wchar_t` is 2 bytes on Windows and 4 on macOS; upstream's text is UTF-16 | **engine**: `wchar_t` → `char16_t`, `L"…"` → `u"…"`, `std::wstring` → `std::u16string`, and std facilities libc++ lacks for `char16_t` → `nppmac::` |
| `std::filesystem::path` is UTF-16 on Windows, UTF-8 on macOS | **engine** sends `std::filesystem` to `nppmac::filesystem`, whose `path` keeps the Windows interface |
| The Win32 API (windows, messages, dialogs, GDI, files, registry, COM…) | **runtime** |
| The Microsoft C runtime (`_wcsicmp`, `swprintf_s`, `%I64d`, LLP64 `%lu`…) | **runtime** |

* **`engine/`** — `npp-migrate`, a tool built on clang's lexer. It rewrites tokens only, so comments,
  strings and line numbers are preserved: compiler messages point at upstream's own lines. Output is
  deterministic and is regenerated by the build whenever upstream changes; it is never committed and
  never edited by hand. `MigrationRulesTest` covers every rule.
* **`migration-fixups.txt`** — the few places where upstream's *logic*, not just its types, assumes
  Windows (today: one). Each replaces an exact piece of upstream text in the generated tree; if
  upstream changes that text, the migration stops and names the fixup, so nothing is silently undone.
  Anything the runtime can handle instead, it does.
* **`runtime/`** — the Windows API Notepad++ uses, implemented on AppKit and Core Graphics.
  Declarations come from [Wine](https://www.winehq.org/)'s headers (LGPL-2.1-or-later), which compile
  on Unix and already use `char16_t` for `WCHAR`. They are downloaded (pinned and hash-checked) and
  generated at configure time; nothing from Wine is committed. `runtime/include/` adds or wraps the
  few headers that differ.
* **`core/`** — compiles upstream's source list (`src_files` in `PowerEditor/src/CMakeLists.txt`,
  read at configure time) from the generated tree.

When upstream starts using something new, the build fails in one of two clear ways — an engine rule
gap or a missing runtime function — never as a merge conflict.

## Building

Requirements: Xcode command line tools, and from Homebrew `llvm` (the engine links clang's libraries)
and `bison` (Wine's IDL compiler needs bison 3).

```bash
brew install llvm bison
cmake -S macos -B macos/build
cmake --build macos/build
ctest --test-dir macos/build
```

The first configure downloads the Wine source release once (about 45 MB) into the build directory.

To see how much of upstream compiles, build every upstream source file:

```bash
cmake --build macos/build --target nppUpstream -- -k
```

## Status

Tracked as job J1 in the work tracker. Today:

* every upstream source file (123 of 123) compiles on macOS, and only three places in upstream are
  adjusted (`migration-fixups.txt`);
* the app links and runs: the main window shows the toolbar, tab bar, Scintilla editor and status
  bar as on Windows, and Notepad++'s menus are in the macOS menu bar;
* files given on the command line open; typing, shortcuts (⌘ acts as Ctrl) and saving work, and
  ANSI code pages decode through iconv;
* Notepad++'s dialogs and panels work: the Open and Save As dialogs are the macOS panels, and
  upstream's own dialogs (Find, Preferences, Style Configurator, Shortcut Mapper, Go To, About,
  Windows…) and docking panels (Function List, Document List…) run on the runtime's controls:
  button, static, edit, list box, combo box, tree view, list view and header, trackbar, progress,
  up-down, link, tooltip and standard scroll bars, drawn as Windows 10 draws them;
* Notepad++'s dark mode works, including "follow Windows", which follows the macOS appearance:
  the editor, panels, dialogs and the runtime's controls go dark, and so do the native menus and
  panels;
* plugins load from `Notepad++.app/Contents/Resources/plugins/<Name>/<Name>.dll`, the place and name
  they have next to `notepad++.exe` on Windows (see [Plugins](#plugins));
* changes made outside Notepad++ show up: Folder as Workspace follows its folders, through
  `ReadDirectoryChangesW` on FSEvents;
* not yet: printing, IME.

The few Win32 functions not implemented yet are weak stubs (printing, IME); the build lists them as
`Win32 functions still stubbed`.

## The app's name and icon

The app's name (bundle, executable, application menu), bundle identifier and icon are CMake
settings:

```bash
cmake -S macos -B macos/build -DNPPMAC_APP_NAME="..." -DNPPMAC_BUNDLE_ID="..." -DNPPMAC_APP_ICON=path/to/icon.png
```

This is Notepad++, so they default to "Notepad++" and upstream's icon, and nothing needs setting.
They are settings only so that a build can differ; upstream's own texts (the Help menu's "About
Notepad++", dialog titles) name Notepad++ whatever they are set to.

## Plugins

A plugin for macOS is built from its Windows sources, with `nppmac_add_plugin` in
[plugins/CMakeLists.txt](plugins/CMakeLists.txt): the sources go through the migration engine as
Notepad++'s do (so `wchar_t` in the plugin interface becomes `char16_t`, as in the app), compile
against the runtime's headers, and link as a Mach-O bundle whose Win32 calls bind to the runtime in
the app. [HelloMac](plugins/HelloMac/HelloMac.cpp), written exactly as for Windows, is the example
and is used by the smoke test.

Plugins Admin shows no list: its list and downloads are Windows binaries.

## Debugging

Environment variables read by the runtime:

| Variable | Effect |
|---|---|
| `NPPMAC_TEST_RUN=1` | a crash prints a backtrace and exits, without the macOS crash report dialog |
| `NPPMAC_SNAPSHOT=<file.png>` | renders the front window to a PNG after `NPPMAC_SNAPSHOT_DELAY` seconds (default 5); `NPPMAC_SNAPSHOT_EXIT=1` then quits |
| `NPPMAC_TEST_TYPE=<text>` | types the text through AppKit, a key every 50 ms, after `NPPMAC_TEST_TYPE_DELAY` seconds (default 2); `^s` is ⌘S, ESC is Escape |
| `NPPMAC_TEST_COMMAND=<id>` | sends a menu command (`IDM_*` value) after `NPPMAC_TEST_COMMAND_DELAY` seconds (default 2) |
| `NPPMAC_TEST_FILE_PANEL=<path>`, `NPPMAC_TEST_COLOR=RRGGBB` | answer the Open/Save panels and the color panel without showing them |
| `NPPMAC_TEST_APPEARANCE=dark` (or `light`) | runs as if the system appearance were so |
| `NPPMAC_DUMP_TREE=1` | with a snapshot, prints the window tree, the native windows and the menu bar |
| `NPPMAC_TRACE_PAINT=1`, `NPPMAC_TRACE_MESSAGEBOX=1`, `NPPMAC_TRACE_WINDOWS=1` | trace painting, message boxes, window creation |
| `NPPMAC_QUIET_STUBS=1` | do not log calls to stubbed functions |

Test runs should use Notepad++'s own `-settingsDir=<folder>` so they leave the real settings in
`~/Library/Application Support/Notepad++` alone.

For example, open a file, type into it, save it and capture the window:

```bash
NPPMAC_TEST_RUN=1 NPPMAC_TEST_TYPE='hello ^s' NPPMAC_SNAPSHOT=/tmp/npp.png NPPMAC_SNAPSHOT_EXIT=1 \
	"macos/build/app/Notepad++.app/Contents/MacOS/Notepad++" -settingsDir=/tmp/npp-settings /path/to/file.txt
```
